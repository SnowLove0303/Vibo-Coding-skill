# 三级功能性真实价值审计与 Agentic 真实路径代测

## 审计目标

代替用户按真实路径完成测试，证明功能是否能在实际入口、实际环境、实际数据和实际状态下产生真实功能价值。三级审计的核心不是“有返回”，而是返回结果是否正确、有用、符合功能用途、能支撑用户真实业务决策或操作。三级代测不是开发自测，也不是只跑辅助脚本。

## 主验收原则

1. 先固定用户真实路径：入口、工作目录、输入方式、运行环境、成功结果、失败标准。
2. 优先使用非鼠标、非抢占式、可复现路径：PowerShell、CLI、API、MCP、脚本、HTTP 探针、程序内置指令、状态查询和日志核验。
3. UI 交互只作为真实用户体验补充；不得用鼠标点击替代指令化能力验证，不得干扰用户当前工作。
4. 辅助测试必须标注与正式路径的差异；辅助失败不能直接覆盖真实路径结果。
5. 所有测试指令必须实际执行一遍，不能把未运行过的命令交给用户。
6. 有返回不等于正确：必须核验返回内容是否符合用户需求、功能用途、业务语义、输入条件、数据事实、权限边界、状态变化和预期结果。
7. 区分审计自跑指令与用户人工测试：三级审计可以记录自己实际执行过的 PowerShell、CLI、API、脚本或日志核验命令作为审计证据，但交给用户的人工测试主流程只能是入口路径、选择、输入、确认、返回/取消/重试、查看结果和异常反馈。不得把长命令、多行脚本、JSON、内部资源编号、`moduleId/action`、`taskId` 或调试 API 包装成用户人工测试步骤。
8. 需要用户授权或输入真实信息时，三级代测应验证并触发 `user-intervention-gateway` 或等价等待式交互脚本/小程序/表单入口：资源隔离授权触发 `ResourceIsolationAuthorization`，正式账号密码登录、验证码或外部风控触发 `FormalLoginInput` 或正式登录入口完成确认，业务信息触发 `BusinessInput`，文件/路径/资源选择触发 `FileOrPathSelection`。授权场景停在允许/拒绝确认，输入场景停在等待输入/选择状态，用户完成后自动继续后续测试。不得把“请用户把值填进命令参数/JSON/配置文件后再运行”作为用户人工测试路径，也不得把可触发网关的事项只写成“仍需人工介入”。
9. 三级测试必须以发出前固化的审计基线为测试清单。若原始需求是 A+B+C，必须分别为 A、B、C 设计并执行用户视角功能性测试，验证每项是否真实接入、结果是否符合功能用途、状态和数据是否正确、旧功能是否未退化。测试方案不能套固定模板，必须根据每个功能的用途、用户入口、输入输出、数据状态、风险和失败影响自行设计。

## 必测项

1. 主成功路径：用户最少操作是否能完成目标，输出是否可判断。
2. 状态同步：操作后页面、列表、汇总、任务记录、日志和事实源是否一致。
3. 实时反馈：耗时操作是否有进度、阶段、完成结果和下一步。
4. 失败恢复：无权限、路径变化、端口占用、依赖缺失、旧进程、缓存残留、登录态失效、超时或异常退出是否可理解、可重试、可取消、可恢复。
5. 旧功能回归：本次改动可能影响的旧入口、共享模块、数据、配置和快捷方式是否仍可用。
6. 多模块独立性：独立模块是否分别验证；一个模块失败是否影响其他模块；提交/推送和回滚证据是否独立。
7. 功能价值：返回结果是否对应真实业务对象、真实数据、正确字段、正确状态、正确时间范围、正确权限和正确动作结果；是否能帮助用户完成目标。
8. 反例识别：空壳返回、固定文案、无关数据、过期缓存、错误字段、假成功、未触发真实动作、状态未同步、数据未落地或业务含义不匹配，均判定为功能缺陷。

## 输出格式

输出必须包含：测试前置条件、真实入口、审计自跑指令与工作目录、用户人工测试交互路径、输入、实际输出、预期结果、功能用途匹配判断、业务语义判断、数据事实核验、状态变化核验、通过/失败标准、证据路径、截图或日志摘要、未覆盖项和继续处理建议。

用户人工测试交互路径必须写成“入口路径 -> 选择项 -> 输入项 -> 确认项 -> 预期可见结果 -> 异常时反馈”。审计自跑指令只能作为证据区或技术附录，不能替代用户人工测试流程。

如流程必须等待用户授权或输入，输出还必须说明交互脚本/小程序/表单的启动方式、等待位置、用户需要授权/输入/选择的内容、完成后的自动继续行为、超时/取消/错误重试方式和敏感信息保护方式。

没有真实路径执行证据时，不得宣称通过、失败、阻断或交付。只有返回结果符合功能用途需求并产生实际功能价值，才能判定三级审计通过。

没有审计基线、没有逐项覆盖原始需求、没有说明每个功能为什么这样测试，或只测试当前可见实现而遗漏原始功能项时，不得判定三级审计通过。
