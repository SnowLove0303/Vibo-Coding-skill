# 二级业务交互审计

## 审计目标

从普通用户和产品经理视角判断功能是否真正可用、可理解、可操作、可恢复，而不是只看底层接口、代码或命令是否成功。

## 必查项

1. 用户真实入口：用户从哪里进入，看到什么，能做什么，是否暴露内部模块编号、任务编号、JSON、状态机或调试命令。
2. 用户最少操作路径：完成目标是否步骤最少、反馈清楚、命名易懂、无需阅读实现细节。
3. 真实能力接入：入口是否连接真实数据、真实接口、真实权限、真实状态和真实错误处理；不得是假入口或静态页面。
4. 实时性与一致性：页面、列表、汇总、任务记录和状态面板是否同步事实源；状态变化、任务结束、异常、资源占用是否自动发现和展示。
5. 进度与反馈：耗时操作是否显示真实进度、当前阶段、完成结果和下一步；不得长时间无反馈。
6. 失败恢复：失败、等待、阻塞、超时和资源占用是否提供等待、重试、取消、返回、恢复或人工处理路径。
7. 旧功能基线：上一正式版本功能、入口、流程、配置、数据链路和用户习惯是否保留；未经授权不得静默消失。
8. 完整需求覆盖：是否对照原始功能需求清单、分段计划和验收标准，而不是只审当前已实现内容。
9. 多模块体验：模块对接后用户路径是否连续，状态和数据是否一致，独立模块失败是否拖累其他模块。
10. 人工测试交互项：交付给用户的人工测试是否只包含入口路径、选择、输入、确认、返回/取消/重试、查看结果和异常反馈；不得把长 PowerShell 命令、多行脚本、JSON、内部编号、`taskId` 或调试 API 当作用户人工测试主路径。
11. 用户接入网关：凡必须由用户接入的环节，是否被收敛为授权确认或信息输入两类；是否使用 `user-intervention-gateway` 或等价交互入口停在等待授权/等待输入状态；是否只调用当前需要的场景，而不是一次展示全部选项；用户确认或输入完成后是否自动继续执行，是否避免让用户手工拼命令参数、JSON 或配置文件。
12. 审计基线覆盖：本次审计是否逐项对照需求与审计线程发出前固化的审计基线。若原始需求是 A+B+C，必须检查 A、B、C 是否都保留、可交互、可验证并符合用户目标；不得只审当前包可见内容或技术线程已实现内容。

## 执行方式

优先使用指令化和非侵入方式获取证据：PowerShell 启动/验证/停止指令、API/MCP/CLI、日志、状态文件、数据库只读查询、截图或录屏证据。需要 UI 观察时，优先使用非抢占工具；鼠标控制只能作为用户交互补充。

## 输出格式

输出必须包含：业务结论、用户路径、旧功能保留情况、新增功能完成情况、状态实时性、失败恢复、人工介入项、证据和阻断项。

若发现静态结果、状态滞后、页面与事实源不一致、响应缓慢、需要反复手动刷新或用户必须理解内部概念，判定为缺陷或交付阻断。

若人工测试文档把技术命令、脚本参数、JSON 或内部调试路径交给用户执行，而不是给出真实交互项路径，判定为交付文档缺陷；影响用户验收时判定为交付阻断。

若报告中出现“仍需人工介入”但没有触发对应用户接入场景，或需要用户授权/输入却没有等待式交互入口，或要求用户自行改长命令、JSON、环境变量、配置文件来继续测试，判定为用户交互缺陷；影响验收连续性时判定为交付阻断。

若缺少发出前固化的审计基线，或审计只覆盖技术线程实际做出的功能，未逐项对照原始 A+B+C 需求、用户入口和旧功能基线，判定为审计依据缺陷；导致需求项遗漏、旧功能静默丢失或用户路径未测时，判定为交付阻断。
