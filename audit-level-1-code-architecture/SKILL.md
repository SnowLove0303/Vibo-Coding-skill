# 一级代码架构审计

## 审计目标

检查技术实现是否真实、简洁、可维护、可回滚，不只判断功能是否表面能跑。一级审计输出必须能支持后续二级业务审计、三级真实路径代测和四级终审复核。

## 必查项

1. 代码简洁性：是否存在臃肿实现、重复逻辑、临时试错残留、无意义抽象或过度工程化。
2. 模块边界：是否按服务、组件、路由、数据访问、调度、命令入口和 UI 分层；是否继续堆进 `main`、主进程或核心聚合文件。
3. 功能完整性：是否围绕完整需求实现，而不是长期停留在最小实现、静态页面、固定文案或一次性查询。
4. 指令化能力：是否具备 PowerShell、CLI、API、MCP、脚本、HTTP 探针、程序内置指令、状态查询或日志核验路径；鼠标点击不能替代系统能力验证。
5. 既有功能保护：是否破坏旧入口、旧流程、旧配置、旧数据、用户习惯、性能基线或跨模块契约。
6. 数据与状态：是否使用真实数据、真实状态、真实错误处理；缓存、快照和推断结果是否标识时间、来源和有效性。
7. 性能与系统重量：启动、运行、打包、内存、依赖、数据库访问、接口调用和资源占用是否退化。
8. 多模块独立性：存在独立模块时，是否分别修改、分别验证、分别提交/推送，并保留独立回滚和证据。
9. 回滚与记录：是否有基线、变更范围、验证证据、回滚路径和风险记录。

## 执行方式

优先使用非控制性方式审计：`rg`、Git diff、构建/测试命令、日志、状态查询、静态分析、脚本和项目自带验证命令。不得为了审计代码而使用鼠标控制或抢占用户界面。

审计前读取执行线程完整记录：任务理解、修改文件、关键命令、失败与重试、自测结果、逐项功能实现汇报、既有功能影响说明和回滚点。

## 输出格式

先列问题，按 P0/P1/P2/P3 排序。每个问题必须包含：位置或证据、影响范围、为什么是问题、建议修复方式、需要回归的路径。

结尾必须给出：通过/不通过结论、已核查范围、未核查范围、既有功能风险、指令化验证证据、多模块独立性判断和回滚建议。
